# Database setup and schema contract

## 1. Important limitation

The supplied repository did not include a `.sql` dump, schema migration, ERD, or seed data. The table and column names below are inferred from JDBC statements in the Java source. They describe what the current application expects; they are **not** a verified copy of the database that the project owner may already have.

Before changing a database, inspect it and back it up. The application currently expects a MySQL database named `library_management_system`.

## 2. Tables and columns referenced by the code

| Table | Columns referenced | Use |
|---|---|---|
| `book_details` | `book_id`, `book_name`, `author`, `quantity` | Book catalogue and available-copy count |
| `student_details` | `student_id`, `name`, `course`, `branch` | Student records maintained by the administrator |
| `issue_book_details` | `id`, `book_id`, `book_name`, `student_id`, `student_name`, `issue_date`, `due_date`, `status` | Loan/return history |
| `users` | `name`, `password`, `email`, `contact` | Administrator sign-up and login in the current implementation |
| `Students` | `name`, `password` | Student-login query in the current implementation |

The current code inserts four positional values into `book_details` and `student_details`, so the existing column order matters unless those statements are changed to explicit column lists. `issue_book_details.id` is read as the loan identifier and appears to be expected to be generated by the database.

## 3. Inspect the current database before applying changes

Run these commands in MySQL Workbench or the MySQL client and save the output for a schema review:

```sql
USE library_management_system;
SHOW TABLES;
SHOW CREATE TABLE book_details;
SHOW CREATE TABLE student_details;
SHOW CREATE TABLE issue_book_details;
SHOW CREATE TABLE users;
SHOW CREATE TABLE Students;
```

On some MySQL installations, table-name case sensitivity differs by operating system. The code's `Students` reference and any differently cased table name must be reconciled explicitly.

## 4. Configure a dedicated database account

After confirming the database exists, create an application account with only the permissions required by the current CRUD flows. Replace the password placeholder with a unique secret and store it outside the repository.

```sql
CREATE USER 'library_app'@'localhost'
IDENTIFIED BY 'replace-with-a-unique-strong-password';

GRANT SELECT, INSERT, UPDATE, DELETE
ON library_management_system.*
TO 'library_app'@'localhost';

FLUSH PRIVILEGES;
```

The application now reads `DB_URL`, `DB_USER`, and `DB_PASSWORD` from the process environment. It also supports `db.url`, `db.user`, and `db.password` JVM system properties. The default username is `library_app`; the password is mandatory.

## 5. Current data and integrity rules

The code currently relies on these exact values and behaviours:

- A newly issued loan is stored with status `Pending...`.
- A returned loan is stored with status `Returned!`.
- A loan is overdue when it remains `Pending...` and `due_date` is earlier than the database's current date.
- Only one pending loan for a specific `(book_id, student_id)` pair is intended at a time.
- `book_details.quantity` is decremented on issue and incremented on return.

These strings should eventually become a constrained status field or enum in the domain layer. Avoid changing their values until the source and database are migrated together.

## 6. Recommended target constraints

Once the actual schema is inspected and existing data is cleaned, add constraints and indexes such as:

- Primary key on `book_details.book_id`.
- Primary key on `student_details.student_id`.
- Primary key / auto-increment on `issue_book_details.id`.
- Foreign keys from `issue_book_details.book_id` to `book_details.book_id` and from `student_id` to `student_details.student_id`.
- `CHECK (quantity >= 0)` on books, if supported and enforced by the deployed MySQL version.
- Indexes on `issue_book_details(status, due_date)`, `issue_book_details(issue_date)`, and `issue_book_details(book_id, student_id, status)`.
- A unique index on normalized account usernames/emails as appropriate.

A simple unique index across `(book_id, student_id, status)` is **not** a correct way to enforce one active loan, because it would also prevent multiple historical returned rows with the same status. Enforce active-loan uniqueness in a transaction with row locking, or design an explicit generated active-loan key and a matching unique index.

## 7. Authentication schema needs a migration

Current behaviour is unsafe and inconsistent:

- `SignupPage` inserts `name`, `password`, `email`, and `contact` into `users`.
- `LoginPage` compares `users.password` directly with the submitted password, indicating plaintext storage.
- `StudentLogin` queries a separate table named `Students` and the same sign-up form does not create records in that table.
- Both login paths open the administrator dashboard.

The recommended target is one `users` table with a hashed password and explicit role, for example `ADMIN` or `STUDENT`, linked to `student_details` for student accounts. Use a password-hashing scheme designed for passwords (PBKDF2, bcrypt, or Argon2), not a plain SHA hash. Remove public administrator registration; create the first admin through a controlled bootstrap process. This requires a coordinated database migration and authentication code change, not only a table rename.

## 8. Circulation transaction design

Issue and return operations must be atomic. The recommended service-level transaction should:

**Issue**
1. Begin a transaction.
2. Lock the target book row (`SELECT ... FOR UPDATE`) and verify available quantity is greater than zero.
3. Verify the student exists and no active loan exists for that book/student pair.
4. Insert the loan row.
5. Decrement available quantity using a guarded update (`quantity = quantity - 1 WHERE quantity > 0`).
6. Commit; roll back every step on any failure.

**Return**
1. Begin a transaction.
2. Lock and load the exact pending loan by `issue_book_details.id`.
3. Change its status only if it is still pending.
4. Increment the referenced book's available quantity.
5. Commit; roll back on failure.

Do not split these steps into separate `Connection` instances. Add integration tests for simultaneous issue attempts, duplicate returns, and failures between the ledger and stock updates.
